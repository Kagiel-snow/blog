软件工程这一课先记住三个问题：系统需要做什么，准备怎样实现，又怎样确认它符合要求。代码只是其中一部分，前面的需求与设计，以及后面的测试，都需要有明确依据。

这篇根据[分享对话中的课程讲解](https://chatgpt.com/share/6ac4b92b-7cbc-83ee-809c-39fd3fe6c1c9)整理，保留日语和英语关键词，方便对照课堂用语。整理依据是分享内容，没有重新逐页核验原课件；涉及课件疑似矛盾的地方，放在文末单独记录。

## 先把开发流程连起来

```text
要求定義 → 外部設計 → 内部設計 → Coding
                                  ↓
受入試験 ← 総合試験 ← 結合試験 ← 単体試験
    ↓
  運用・保守
```

| 阶段 | 要回答的问题 | 可以留下的成果 |
| --- | --- | --- |
| 需求定义 / 要求定義 | 系统需要完成什么，受哪些条件限制？ | 需求规格、验收条件 |
| 外部设计 / 外部設計 | 用户怎样操作，输入输出是什么？ | 界面、操作流程、外部接口说明 |
| 内部设计 / 内部設計 | 模块怎样组织，数据怎样处理？ | 模块接口、数据结构、处理步骤 |
| 编码 / コーディング | 怎样把设计实现出来？ | 源代码 |
| 测试 / 試験 | 实现是否符合规格，哪里存在缺陷？ | 测试用例、实际结果、问题记录 |

课堂以瀑布模型（滝型開発 / Waterfall Model）说明阶段关系：原则上先完成并确认前一阶段，再进入下一阶段。这样做是为了减少手戻り（返工 / Rework）。实际项目仍可能返回前面的阶段修改，也可能采用迭代开发，不能把这条顺序理解成所有项目都只能走一次。

## 系统比软件的范围更大

系统（システム / System）由相互关联的要素组成。一个购物系统除了程序，还包括数据库、服务器、网络、用户、管理员，以及支付和物流等外部服务。

设计时，不同角色关注的内容也不同：用户关心操作和信息安全，开发者关心实现与维护，运维人员关心监控和故障恢复，经营者关心成本与收益。因此，系统设计需要同时考虑功能、人员和运行方式。

## 需求定义：把想法写成能检查的要求

要求定義（ようきゅうていぎ / Requirements Definition）先确定 **What：需要做到什么**。设计再逐步回答 **How：怎样做到**。

“需要一个快的网站”还不够明确。可以进一步约定：在指定网络、数据量和并发负载下，95% 的请求在 2 秒内完成。数字只是示例，关键是同时写清测量条件与通过标准。

### 功能需求与非功能需求

| 类型 | 关注点 | 例子 |
| --- | --- | --- |
| 機能要求 / Functional Requirement | 系统提供什么行为 | 学生输入出席码后，系统登记出席时间 |
| 非機能要求 / Non-functional Requirement | 质量达到什么程度、受什么限制 | 指定负载下的响应时间、可用性、兼容性 |
| 项目或技术约束 / Constraint | 开发必须遵守什么条件 | 预算、交付期限、指定 Java 或数据库 |

课程把预算、期限、指定技术等放在广义的非功能要求中记忆即可；实际文档也可能把它们单列为约束。

不要只看一句话里有没有“安全”就分类。例如“双因素认证”可以具体写成系统功能，而“只有授权用户才能访问记录”还需要权限规则与相应的验证方法。需求分类服务于理解和检查，不能代替对行为的描述。

完成需求定义后，要把功能、约束、运行条件与验收标准写进要求仕様（Requirements Specification）。否则，开发和测试很容易各自理解一套规则。

## 外部设计和内部设计怎么分

用出席登记系统对照比较容易记。

| 层次 | 示例 |
| --- | --- |
| 需求定义 | 学生能够登记当前课程的出席 |
| 外部设计 | 登录 → 选择课程 → 输入出席码 → 提交 → 显示登记结果；错误时提示原因 |
| 内部设计 | 校验身份与出席码，检查有效时间和重复记录，调用数据库保存，再返回结果 |

**外部设计看外部可观察的行为，内部设计把处理细化到可以编码的程度。** 外部设计不仅是界面的颜色，还包括输入规则、输出内容、错误提示，以及与外部系统交互的接口。

内部设计需要明确模块（モジュール / Module）的职责、输入、输出、异常情况和调用关系。例如文件单词统计可以拆成读取文件、提取单词、累计计数和输出结果几个部分。

### DFD 与流程图关注点不同

DFD（データフロー図 / Data Flow Diagram）关注数据从哪里来、经过什么处理、保存在哪里、流向哪里。

| DFD 要素 | 作用 | 示例 |
| --- | --- | --- |
| 外部实体 / External Entity | 数据来源或接收者 | 学生、外部支付服务 |
| 处理 / Process | 将输入数据转换成输出数据 | 验证出席码 |
| 数据存储 / Data Store | 保存数据 | 出席记录库 |
| 数据流 / Data Flow | 标明传递的数据及方向 | 出席码、登记结果 |

分享讲解把课件中的「アクティビティ」对应到数据来源或去向；这里用“外部实体”说明其作用，课堂具体符号仍以课件为准。

下面只是文字表示的数据流关系：

```text
学生 ──出席码──→ 登记处理 ──出席记录──→ 记录库
学生 ←─登记结果── 登记处理
```

箭头旁应该写清传递的数据。流程图（フローチャート / Flowchart）则更关注执行先后、条件判断和循环；两种图不能仅因为都有箭头就混为一谈。

### 用十连抽例子再对照一次

分享内容用ガチャ说明三个层次：

1. **需求**：连续抽取十次，按概率决定角色，展示结果，并定义保底规则。
2. **外部设计**：玩家点击抽取按钮，看到演出和结果列表，能够返回。
3. **内部设计**：读取角色与概率数据，生成随机数，决定结果，更新持有角色与保底计数，再返回展示数据。

“有保底”还需要继续细化：第几次触发、抽中后是否清零、十连过程中能否触发。规则没有确定，就无法可靠地写出预期结果。

## 四个测试层级分别确认什么

| 日语 | 英语 | 检查重点 |
| --- | --- | --- |
| 単体試験（たんたいしけん） | Unit Testing | 一个函数或模块的行为是否正确 |
| 結合試験（けつごうしけん） | Integration Testing | 模块之间的接口、数据和调用是否匹配 |
| 総合試験（そうごうしけん） | System Testing | 整个系统的功能与质量是否符合系统规格 |
| 受入試験（うけいれしけん） | Acceptance Testing | 是否满足用户需求与约定的验收条件 |

比如登录模块和数据库模块单独都正常，但一个传用户编号，另一个要求用户名，连接后仍然会出问题。这就是集成测试需要检查的内容。

V 字模型的重点是：**测试要能追溯到相应的需求和设计，测试准备可以提前开始。** 验收对应用户需求，系统测试对应系统规格，集成测试对应结构和接口设计，单元测试依据模块的详细规格。分享讲解用“Coding 对应单体测试”帮助记忆，但预期结果不能仅由已经写出的代码决定，否则错误实现可能被当成正确答案。

### Driver 和 Stub

| 名称 | 替代哪一侧 | 例子 |
| --- | --- | --- |
| ドライバ / Test Driver | 调用被测模块的上层 | 临时程序给价格计算函数传入参数并检查结果 |
| スタブ / Stub | 被测模块调用的下层 | 临时服务返回约定的支付响应 |

记忆方向：**Driver 调用被测模块，被测模块调用 Stub。** 自底向上的集成常用 Driver，自顶向下的集成常用 Stub。替身测试通过后，仍要验证真实模块连接。

## 测试层级和测试方法分开记

“单元、集成、系统、验收”描述测试范围和目的；“黑盒、白盒”描述设计测试时依据什么。单元测试也可以采用黑盒方法。

| 区分方式 | 方法 | 含义 |
| --- | --- | --- |
| 是否执行程序 | 机上確認 / Static Testing | 不运行程序，通过评审需求、设计或代码等发现问题 |
| 是否执行程序 | 動作確認 / Dynamic Testing | 执行程序，比较实际结果和预期结果 |
| 用例依据 | ブラックボックス / Black-box | 根据规格和外部行为选择输入、判断输出 |
| 用例依据 | ホワイトボックス / White-box | 根据内部结构、语句和分支设计测试 |

白盒测试里还要区分语句覆盖、分支覆盖与条件覆盖：执行到一条语句、让整个判断出现真假结果、让各个子条件出现真假结果，是不同的要求。

测试能够发现缺陷，但通常不能证明系统绝对没有缺陷。通过若干用例，只能说明在这些测试条件下没有观察到相应问题。

## 等价类划分与边界值分析

### 同値分割：先按预期行为分组

同値分割（どうちぶんかつ / Equivalence Partitioning）把输入划分成预期处理方式相同的类别，从各类选择代表值。

假设整数输入允许范围为 `1～100`：

| 类别 | 代表值 | 预期行为 |
| --- | --- | --- |
| 小于 1 | 0 | 拒绝或报错 |
| 1 到 100，含端点 | 50 | 接受 |
| 大于 100 | 101 | 拒绝或报错 |

这里分组的依据是“是否接受”。如果范围内还存在不同收费档位，就需要继续划分。代表值测试是降低成本的方法，不意味着同一类所有值都已经实际测过。

### 境界値分析：检查规则改变的位置

境界値分析（きょうかいちぶんせき / Boundary Value Analysis）重点检查边界及附近的值，容易发现 `<`、`<=` 或临界位置写错的问题。

对于允许长度为 `1～100` 的字符串，课堂式边界练习可选择：

```text
下限附近：0、1、2
上限附近：99、100、101
```

这里测试的是长度。若还要求只能包含半角字母，字符种类也要另行设计用例；`null` 与长度为 0 的空字符串也不是同一个输入。

“边界减一、边界、边界加一”适合这类整数或计数示例。连续量、日期、浮点数等需要按数据精度与规则确定邻近值。正式的边界覆盖还应区分各个等价类的端点与采用的覆盖准则，不能把课堂选点口诀直接当作完整定义；可对照 [ISTQB CTFL 大纲 4.2.2 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)。

### 条件组合多时先列决策表

决策表（決定表 / Decision Table）把条件组合与相应动作列出来，再排除不可能的组合，能减少遗漏。

分享中的字符串例子同时涉及长度、第一个字符、第二个字符和最后一个字符。不能只检查首尾而忘记第二个字符；长度为 2 时，第二个字符就是最后一个字符，要求它同时等于 `b` 和 `z` 的组合不可能成立。

测试记录至少包含：输入、预期结果、实际结果和是否通过。**先根据规格写预期，再运行程序记录实际结果。**

## 最后一题：a 和 b 都大于 7

题目要求两个 `int` 值都大于 7 时输出一句话：

```java
if (a > 7 && b > 7) {
    System.out.println("両方とも 7 より大きい");
}
```

### 先看判断条件

`&&` 是論理積（Logical AND / 逻辑与），两个条件都为真，整个判断才为真。

| a > 7 | b > 7 | 整体结果 |
| --- | --- | --- |
| false | false | false |
| false | true | false |
| true | false | false |
| true | true | true |

题目的阈值是 7。对每个变量选择 `6、7、8`，检查小于、等于和大于阈值的情况。两边各有三个候选值，组合得到九个用例。

### 按题目格式记录答案

```text
6,6:出力なし
6,7:出力なし
6,8:出力なし
7,6:出力なし
7,7:出力なし
7,8:出力なし
8,6:出力なし
8,7:出力なし
8,8:両方とも 7 より大きい
```

`出力なし` 是对“没有输出”的记录，不是程序会打印这几个字。原代码没有 `else`，所以条件不成立时不会输出这条消息。最后一行保留源码字符串中数字 7 两侧的空格。

### 为什么 7,8 和 8,7 很重要

只测 `(7,7)` 并不总能发现某一边把 `>` 写成 `>=` 的错误：另一边仍然为假，整个 AND 依旧为假。

- `(7,8)`：让 b 一侧成立，专门暴露 a 一侧是否错误地包含 7。
- `(8,7)`：让 a 一侧成立，专门暴露 b 一侧是否错误地包含 7。
- `(8,8)`：确认两个条件成立时确实输出。

源码中的 `a = 8; b = 9;` 只是一次固定赋值。设计用例时，把 a、b 当作可变化的测试输入；实际执行时再替换赋值或编写测试入口。

这九组是分享练习围绕阈值选出的组合，不代表覆盖所有整数输入，也不声称是任何边界覆盖标准下唯一或最小的完整测试集。

## 复习时记住这些词

| 中文 | 日本語 | English |
| --- | --- | --- |
| 需求定义 | 要求定義・要件定義 | Requirements Definition |
| 外部设计 | 外部設計 | External Design |
| 内部、详细设计 | 内部設計・詳細設計 | Internal / Detailed Design |
| 数据流图 | データフロー図 | Data Flow Diagram |
| 等价类划分 | 同値分割 | Equivalence Partitioning |
| 边界值分析 | 境界値分析 | Boundary Value Analysis |
| 决策表 | 決定表 | Decision Table |
| 预期结果 | 期待結果 | Expected Result |
| 返工 | 手戻り | Rework |

对话最后想表达的是“这道题的要点是边界值分析”：

> この問題のポイントは境界値分析です。  
> The key point of this exercise is boundary value analysis.

这里 `point / ポイント` 是“要点”，`boundary / 境界` 才是“边界”。

## 留下的核对项与自测

分享讲解提到：字符串规则写着“长度不足 2 时显示错误”，后面的示例表却列出单字符输入及布尔结果。由于这里没有直接核验原 PDF，先把它记作**待核对项**，不据此断言课件有错。做题时先确认有效规格，也要确认长度超过 10 时应怎样处理。

复习时可以遮住正文，回答下面五个问题：

1. “学生能够登记出席”和“按钮点击后显示哪些信息”，分别属于哪个阶段？
2. 单个模块都通过测试，为什么还需要集成测试？
3. 被测模块要调用一个尚未完成的服务，应该准备 Driver 还是 Stub？
4. 为什么只测一个普通有效值，容易漏掉边界错误？
5. 如果把 `&&` 改成 `||`，九组输入中哪些会输出？

参考答案：① 需求定义、外部设计；② 接口或数据约定仍可能不匹配；③ Stub；④ 无法区分临界处的包含或排除规则；⑤ `(6,8)、(7,8)、(8,6)、(8,7)、(8,8)`。
